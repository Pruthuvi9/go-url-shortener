⏺ Here's my review of the solution design:

  ---
  Solution Design Review

  What's solid

  - Clear separation of functional vs non-functional requirements
  - Correctly identifying the read/write asymmetry as a key consideration — this
  is the most important insight for this system
  - 302 over 301 for redirect is the right call (301 is browser-cached, losing
  analytics)
  - Graceful shutdown pattern in main.go is already good infrastructure to build
  on

  ---
  Gaps and Issues

  1. Shortcode generation strategy is undefined
  The flow says "Generate short URL" but not how. The three common approaches
  have meaningful trade-offs:
  - Counter + Base62: simple, predictable, no collisions — but exposes creation
  volume
  - Hash (MD5/SHA of URL, take 6–7 chars): deterministic, deduplication is free
  — but needs collision handling
  - Random ID: unpredictable — but requires collision checks on every write

  This needs a decision and a collision-handling path in the flow.

  2. No caching layer
  Your NFRs require <100ms redirect and 100M DAU, but there's no mention of a
  cache. The redirect path (GET /{code}) will be read-heavy by orders of
  magnitude vs writes. A cache (e.g. Redis) for short_code → long_url is
  essential here. You'd also need to think about TTL and invalidation on expiry.

  3. Expiration is partially modeled
  You accept expiration_date in the request but the redirect flow doesn't handle
  the expired case. It should branch: expired URL → return 410 Gone (not 404 —
  semantically different: the resource existed but is no longer available).

  4. User entity isn't wired up
  It's listed as a core entity but never appears in the API or flows. Is auth
  required to create a URL? Is there per-user rate limiting? If users aren't
  needed for V1, remove the entity to avoid confusion.

  5. API endpoint naming
  GET /short_urls reads like a collection listing. It should be GET 
  /{short_code} — the code is the path param, not a query string.

  6. Duplicate URL handling not addressed
  If the same long URL is submitted twice, should it return the same short code
  (deduplication) or a new one? Hash-based generation gives you deduplication
  for free; counter-based doesn't. Worth an explicit decision.

  7. Database choice/sharding omitted
  At 1B URLs you'll need sharding. The design should state the DB choice and the
  shard key (likely short_code). No need for a deep dive but "save to DB" is
  too vague for a system at this scale.

  8. Custom alias validation rules missing
  What characters are allowed? Is there a length limit? How do you prevent
  collision with reserved paths (/api, /health, etc.)?

  ---
  Minor notes

  - The main.go is currently a learning playground and has no relation to the
  design — that's fine for now, but the first implementation milestone isn't
  clear from the doc.
  - Consider adding a DELETE /urls/{short_code} for cleanup/expiry management,
  even if it's a V2 feature.
  - URL validation: clarify whether "is the URL valid?" means format-only
  (regex) or live reachability check. Format-only is almost always the right
  call for latency reasons.

  ---
  Priority order for gaps

  1. Define shortcode generation + collision handling
  2. Add caching to the redirect flow
  3. Handle the expiration case explicitly (410 vs 404)
  4. Fix the API endpoint path
  5. Decide on User auth / remove the entity if not needed for V1

  Your decisions applied:
  - SHA-256 → Base62 → 7 chars for shortcode generation; collision handled by
  re-hashing with an incrementing counter suffix
  - Valkey as the caching layer with write-through on create, DEL on delete, TTL
  derived from expires_at
  - 410 Gone for expired URLs (and expired entries are not re-cached)
  - Auth noted as V2 in requirements and entity list, no user_id in the schema
  yet
  - GET /{short_code} corrected, DELETE /urls/{short_code} added
  - Hash-based deduplication explicitly called out

  Suggestions made:

  - DB (point 7): PostgreSQL with short_code as primary key. At ~200 GB for 1B
  rows it fits a single large instance for a long time; sharding path is by
  first character of short_code or consistent hashing when writes eventually
  saturate.
  - Custom alias validation (point 8): Characters [a-zA-Z0-9_-], length 3–20,
  case-sensitive, plus a reserved-path blocklist to prevent aliasing system
  routes like api, urls, admin.

  ---
  The key rule: dependency arrows point inward only.

  handler → usecase → domain
  repository → usecase (implements its interface)
  cache      → usecase (implements its interface)

  usecase/ports.go defines the interfaces; repository/ and cache/ implement
  them. The use case layer never imports postgres or valkey packages — it only
  knows about the interfaces it owns. This is what makes the layers
  independently testable.

  ---
  Why each directory exists:

  ┌──────────────────────────────┬───────────────────────────────────────────┐
  │             Dir              │                   Role                    │
  ├──────────────────────────────┼───────────────────────────────────────────┤
  │ cmd/api                      │ Entry point only — reads config,          │
  │                              │ constructs dependencies, starts server    │
  ├──────────────────────────────┼───────────────────────────────────────────┤
  │ internal/domain              │ Pure entities and sentinel errors; no     │
  │                              │ imports from your own code                │
  ├──────────────────────────────┼───────────────────────────────────────────┤
  │ internal/usecase             │ Business logic + port interfaces;         │
  │                              │ framework-agnostic                        │
  ├──────────────────────────────┼───────────────────────────────────────────┤
  │ internal/handler             │ HTTP concern only — parse request, call   │
  │                              │ usecase, write response                   │
  ├──────────────────────────────┼───────────────────────────────────────────┤
  │ internal/repository/postgres │ DB adapter; implements URLRepository      │
  ├──────────────────────────────┼───────────────────────────────────────────┤
  │ internal/cache/valkey        │ Cache adapter; implements URLCache        │
  ├──────────────────────────────┼───────────────────────────────────────────┤
  │ pkg/shortcode                │ Stateless utility; could be used outside  │
  │                              │ this service                              │
  ├──────────────────────────────┼───────────────────────────────────────────┤
  │ pkg/validator                │ Same — pure functions, no state           │
  ├──────────────────────────────┼───────────────────────────────────────────┤

  ---
  internal/ vs pkg/: Code under internal/ cannot be imported by other Go modules
  — it's private to this service. pkg/ is for utilities pure enough that
  another service could theoretically reuse them. If you're unsure, default to
  internal/.
